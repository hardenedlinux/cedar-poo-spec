#+TITLE: Tool-Using Language-Model Security Across Data and Tool Effects
#+OPTIONS: toc:nil

* Namespace and architectural boundary

=AgenticAI= is the [[file:../README.org][top-level reusable library]] for
tool-effect checks; =AgenticAI.LanguageModel= names the tool-using system described in the cited
LLM-agent papers: a language model proposes multi-step actions using tool
observations. It does not name a Cedar principal, a human delegate, or a model
that only returns text. Generic source, approval, delegation, and admission
rules remain in =Data=, =Governance=, and =Admission=. This namespace owns the
language-model workflow and its external-effect acceptance cases. The model's
proposal is untrusted input; Cedar and the Host enforce the effect boundary.
The [[file:../Boundary.lean][typed AgenticAI boundary]] composes action and
sink checks through LeanPoo multiple dispatch. A selection or deletion whose
survivor set is externally observable enters the same release path as a write.

An action proposed by a tool-using language-model system can cross data, model,
tool, and storage boundaries after each individual gateway has accepted its
local operation. The reusable SPEC
control is an exact-effect admission contract: POO composes the independently
owned policy and evidence requirements; Cedar decides on the currently
projected request; a Host authenticates observations, rechecks revisions, and
atomically records admission before attempting the external effect.

The [[file:../../Admission/BoundOperation.lean][BoundOperation]] API binds an effect to its projected request.
The [[file:../../Data/Lineage.lean][Lineage]] and [[file:../../Data/CumulativeDisclosure.lean][CumulativeDisclosure]] modules model source
ancestry and cumulative release state. The [[file:../../../Examples/Health/AgenticAI/LanguageModel/Disclosure.org][hospital language-model disclosure case]]
combines them with scoped approval, delegation, and Cedar policy replay.
The [[file:../../../rust/disclosure-host/src/host.rs][process-local Rust Host reference]] rechecks the
composed Cedar policy and commits the [[file:../../../rust/core/src/authority_consumption.rs][approval-instance ledger]],
[[file:../../../rust/core/src/operation_identity.rs][operation ledger]], disclosure ledger, and audit under one lock. These
models do not authenticate source data or supply a durable transaction.

* Reading the papers as Gateway proof obligations

The threat model distinguishes three actors. An agent proposes an exact
tool effect. A reviewer can contribute evidence or advise on a fallback.
The Gateway and the final receiver enforce the independently configured
authorization, provenance and consumption rules. The proposer and reviewer
can see adversarial content. Their agreement does not authenticate the
destination, source ancestry, external result or current authority cut.

** FLOWSEAL: observe effects across channels

[[https://arxiv.org/abs/2609.14003][Shim et al.]] report attacks based on collaborative workspaces,
observable omissions and separating instructions from the eventual
disclosure channel. Tool interception outside the model addresses the
enforcement boundary. A deployment still has to identify which effects and
metadata its observers can see. For example, removing all but selected rows
reveals the survivor set to a collaborator who can compare versions, even
when the agent produces no confidential text.

A finite counterexample now runs against the existing Lean ledger in
[[file:../../../Tests/AgenticAI/Boundary.lean][Tests.AgenticAI.Boundary]]. A workspace edit leaves candidates
={p1,p2}= and a tool response leaves ={p2,p3}=.
Both pass a minimum of two against the initial inventory. A shared ledger
refuses the second release in either order because the intersection is
={p2}=. This proves a property of the modeled candidate observations.
The Host must authenticate the observed survivor set and decide which
recipients can combine their views. An unmodeled observer or channel
remains outside the result.

** OCELOT: separate a proved charge bound from inferred privacy

[[https://arxiv.org/html/2606.12341v1#A2][Xie and Li, Appendix B]]
prove a ledger charge bound separately from the inference claim. The latter
depends on cost calibration covering the adversary's observations.
Section 4.3 makes the dependency assumption explicit for additive operator
costs and handles declared dependent pairs jointly. The paper also evaluates
residual escapes from omission or labeling errors. A proof that a budget
never went negative cannot establish the fidelity of the candidate set,
the completeness of the sink map or a bound on posterior inference.

A Gateway extension can bind the exact output, its transformation witness,
the observer scope and the current ledger revision. Costs or candidate sets
must be derived by the trusted verifier from the evidence. A model-supplied
numeric charge is only a proposal. Existing candidate cardinality has a
different meaning from OCELOT's calibrated min-entropy measure. Both the
cost model and the enforcement result should retain their own provenance.

** Delegated review: a vote threshold is a policy parameter

[[https://arxiv.org/abs/2609.15803][Collina et al.]] characterize safe threshold review under assumptions
about the reviewers' utility differences and their reporting. With up to
=k= disapprovals, the condition must hold for the remaining coalition after
each possible removal of =k= reviewers. Counting signatures establishes
which reviewers approved. It gives no evidence that any such coalition
represents the principal's utility. The paper's sequential result uses a
designated baseline and continuation-aware values in a discounted MDP.
Its strategic-voting analysis has separate assumptions. This reading uses
the authors' abstract for those claims.

For SPEC, the immediately testable property is narrower. A panel may
propose a branch or supply bounded evidence. The receiver still checks
the actual Cedar input, current cut, exact effect, and cumulative state.
The existing [[file:../../Authorization/Delta/Trace.lean][Delta trace]]
replays a fixed proposal list across two policy roots. An adaptive agent
may change its next proposal after seeing a denial or tool result.
A trajectory guarantee therefore needs an explicit fallback and a step law
quantified over all admitted proposals in the declared model.

| Adversarial control | Existing owner | Evidence required for a stronger claim |
|---------------------+----------------+----------------------------------------|
| Observable selection across tools | =AgenticAI.Boundary= and =Data.CumulativeDisclosure= | Bind the actual survivor set and jointly observable history at the sink. |
| Two stale permits competing for one release budget | =ZeroTrust.Observation= and the disclosure Host | Prove current-revision reservation and replay both commit orders with one shared ledger. |
| A lost reply followed by replanning | =Gateway.Lifecycle= and the provider audit | Bind the original operation and outcome, retain the charge while unknown, and refuse a second dispatch. |

* Distinct identities and the unresolved effect gap

An approval-instance ID identifies one authorized use. A logical-operation ID
identifies one requested disclosure across retries and replanning. A
dispatch-attempt ID would identify one outbound call and its result. These
identities cannot be inferred from the output digest: a new, separately
approved disclosure may legitimately send the same bytes, while one retry
must not become a new operation merely because the Agent obtained another
approval.

The current [[file:../../../rust/disclosure-case/examples/agentic_ai_language_model_disclosure_host.rs][Host example]] checks =crossApprovalReplayDenied=: a fresh approval cannot
admit the same logical operation again. =distinctApprovalAccepted= uses a
different operation ID with the same payload, demonstrating an independent
disclosure while budget remains. [[file:../../Admission/OperationIdentity.lean][Lean]] and [[file:../../../rust/core/src/operation_identity.rs][Rust]] expose the
operation ledger. =CommitReceipt= records process-local admission before any
sink call; it is not a delivery receipt.

The safe execution contract needs one durable record keyed by logical
operation and exact effect. The admission transaction must consume approval,
reserve budget, and record pending dispatch together. Before issuing the
external call, the Host must record that dispatch may have begun. A known
success may become =succeeded=; a verified refusal before any effect may
become =confirmed_no_effect=; a timeout or lost response must remain
=unknown=. An =unknown= operation cannot obtain a fresh approval and be
blindly dispatched again. Reconciliation needs authenticated target evidence,
or a target-supported idempotency key derived at the adapter boundary and
retained for the required retry horizon. An outbox alone gives no
exactly-once guarantee at the target.

An uncertain effect must keep its effect-budget reservation. A confirmed
no-effect result may release that reservation in a recorded correction, but
it cannot silently restore the consumed human approval. A rate budget counts
attempts and should not be released merely because the effect failed. The
current Rust Host debits budget at admission and does not persist
remote outcome reports or budget corrections; its conservative debit
is therefore not evidence of completed delivery.

Cedar's [[https://github.com/cedar-policy/cedar-spec/blob/main/cedar-lean/README.md][verified symbolic equivalence and implication checks]] compare policy
behavior. They do not answer whether an already admitted operation reached a
remote sink. POO can compose the policy owners and effect-class requirements;
the durable operation journal and result reconciliation belong to the Host.
The Host must obtain logical-operation identity from an authenticated workflow
record; neither a POO prototype name nor a new approval ID can mint that
identity on the Agent's behalf.

* Process-local receiver replay

One disclosure Host instance owns one jointly observable cohort. Prepared
tickets carry that instance's identity and the shared revision alongside the
exact effect, including its channel and audience. The receiver refuses a
ticket from another instance even if every revision number matches. The
existing transaction checks the current evidence, records the narrowed
cohort, consumes approval, debits budget and reserves the logical operation
before any dispatch callback. The Lean release model proves that a successful
release advances the shared revision and retires competing tickets across
channels.

The Rust healthcare replay covers both delivery orders for distinct channel
tickets prepared against the same authenticated observation. It also
simulates one external attempt followed by a lost reply. A different
channel and unused approval cannot send again under the same logical
operation. The original budget charge and operation reservation survive.
=DispatchOutcome::Unknown= reports uncertainty to the caller. The
process-local Host retains the admission as a conservative barrier and
does not provide durable outcome settlement. The trusted dispatch adapter
must send the exact admitted effect. Remote fencing and authenticated
reconciliation are separate deployment obligations.

* Restart reservation and receiver fencing

The Unix dispatch journal reserves the authenticated logical operation before
a send can run. The immutable file binds that operation to the complete effect
digest and to the receiver scope and generation. Creation is exclusive. The
file and containing directory are synchronized before dispatch. A partially
written reservation fails closed. The trusted directory must remain bound to
one workflow authority across restart. The journal is a dispatch barrier.
The deploying Host must restore budget, cohort, approval and audit state from
its own transaction. A crash after reservation but before send can require
operator resolution, because automatic retry could duplicate an effect.

The receiver checks the independently supplied current scope and generation
and recomputes the exact observed effect binding. It reserves the operation
in its own journal before applying the effect. The simulation orders control
updates and application under the same lock. A real transport must authenticate
the sender and recover the current cut from its trusted control plane before
accepting a request. Reading an old cut or letting the request choose the cut
would defeat receiver fencing.

A detached provider outcome is verified against an independently configured
provider key and the exact retained binding. Its result does not release the
send reservation. The native replay drops the original mediator, reopens the
same journal, and tries a different channel and approval before and after
reading the signed outcome. It also replays the original request at the
receiver and presents a delayed request after a receiver cut change.
This is a local filesystem and simulated receiver qualification. It does
not implement a network transport or a production provider outcome store.

* Host transaction contract

1. Resolve the current source, token, transformation, purpose, delegation,
   policy revision, intended output, and final sink audience from authenticated systems.
2. Project those facts to the current POO-composed Cedar policy and require an
   error-free Allow for the exact proposed effect.
3. Within one serializable transaction, compare the ticket epoch and all
   revisions again, including sink membership and recipient-grant revisions;
   require one exact, unspent approval instance and an
   unadmitted logical operation; consume the approval, admit the operation,
   debit budget, update cumulative disclosure state, and write the audit
   event. Abort the entire transaction on any failure.
4. Only after admission commit may the Host attempt the external effect. A
   retry after a known no-effect result requires a fresh decision against
   current state. An uncertain result must be reconciled or retried through
   the target's idempotency contract for the same logical operation; a new
   approval and ticket alone do not make re-execution safe.

The process-local Host example executes reauthorization and one in-memory
commit; it is not the durable Host required by this contract. Production
closure additionally requires authenticated provider and query receipts,
authenticated operation identity, a durable journal, transaction and effect execution tests, and a deployment-specific
privacy assessment. The cited sources do not claim that SPEC has completed
those integrations.
