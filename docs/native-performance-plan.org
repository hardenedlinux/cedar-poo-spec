* Scope and evidence boundary

The owner is the shared Rust runtime/catalog and the shared Lean Functional
object layer. All 51 catalog entries, 23 schema-bearing manifests, nine object
families and applicable Production fixtures remain one acceptance unit. Domain
fixtures consume shared changes; there is no per-industry engine, provider or
independently declared completion. PR #8 remains open and unmerged.

This document distinguishes implemented observations/ownership changes from
planned entity preparation, typed transport and Lean allocation work. Those
planned optimizations are not claimed as implemented or qualified.

* Why the earlier process comparison was inconclusive

The earlier baseline/current observation was 2.150/2.187 seconds per process,
although the sum of the three replay+serialization samples was 1.546/1.490
seconds. Thus unsampled work was 604.1/697.1 ms, an increase of 93.0 ms against
a 55.6 ms sample reduction. That single fixed-order pair could not identify
startup regression or qualify an end-to-end speedup.

The benchmark source proves that a process additionally executes one full
unmeasured catalog replay as its warmup/reference, reparses the complete input
to count revisions, compares outputs, constructs observations and drops values.
The OS observer includes executable launch, stdin reading, final output and
teardown too. These costs must not all be labeled startup. The historical
93 ms difference cannot be retrospectively assigned to a particular phase;
that run did not record those phases.

A bounded three-pair repeat alternated process order without changing any
process's warmup, three samples or 120-second ceiling:

| Pair and order | Baseline process s | d1fc4fa process s | Baseline outside samples ms | d1fc4fa outside samples ms |
|----------------+--------------------+------------------+-----------------------------+---------------------------|
| 1 current/baseline | 2.194 | 2.091 | 612.6 | 586.1 |
| 2 baseline/current | 2.189 | 2.091 | 609.1 | 580.1 |
| 3 current/baseline | 3.647 | 2.525 | 880.7 | 656.3 |

Current was lower in all three pairs, while the third pair showed substantial
host variation. This refutes treating the original single pair as an established
repeatable regression. It does not establish a general speed ratio or tail
latency bound. A separate one-second native CPU stack sample observed entity
parsing, JSON conversion, allocation and destruction paths. Sampling perturbs
the process and covers a window; its timings are not latency qualification or
whole-run CPU percentages.

* Implemented common ownership and lifecycle changes

The catalog moves its already encoded nested Values into the final JSON object,
removing a redundant deep serialization. It retains manifests/typed receipts
only for the existing cross-artifact consumers: pseudonymization deployment,
claim settlement claims and banking. The remaining schema manifests finish
at their own entry; all still replay before retirement. The required three
inputs remain available until all cross-artifact checks finish. This is a
logical retained-manifest count, not an RSS bound.

The ordinary replay path adds no clocks. The existing benchmark now reports:

- Lifecycle: reference warmup, revision-inventory parse/count/drop, complete
  sample loop, reference cleanup, bookkeeping and measured benchmark body.
- Samples: replay, comparison, serialization, explicit output cleanup and wall
  time; complete receipt equality and authorization/preparation counters remain.
- Catalog: input decode, entry loop, cross-artifact/output finalization and
  explicit retained-manifest cleanup; every catalog name has an observation.
  Deferred deployment/handoff entries record capture costs, while their actual
  validation costs are in finalization. Entry records and stages are different
  views and must not be added together.

Stage sums are checked for overlap. OS elapsed minus measured benchmark body
is an external residual including launch, CLI setup/stdin, final report output,
remaining drops, shutdown and observer overhead. It is not isolated dyld time,
a cold-filesystem measurement, or Python/uv startup time: the wrapper starts
its timer after importing itself and hashing the executable.

** Shared Entities preparation: first substantive candidate

A source-input survey found 1280 case rows but only 51 distinct entity JSON
snapshots when identity is scoped separately to each manifest. This is an input
inventory, not proof of authorization equivalence or evidence of implemented
reuse. The current case path reparses entities for every row; request preparation
was around 145 ms per complete sample in the earlier phase observations.

Use the pinned [[https://docs.rs/cedar-policy/4.12.0/cedar_policy/struct.Entities.html][Cedar 4.12.0 public Entities API]]. Its parser validates with the
supplied schema and incorporates schema action entities. Therefore a UID or
JSON digest alone is insufficient for reusing parsed entities.

The proposed slot must own or borrow the actual schema for one invocation and
retain the full source snapshot alongside parsed Entities. Lookup verifies full
source equality; changes replace the slot, and invocation exit releases it.
No global cache, cross-schema reuse or decision/credential retention is allowed.
Construction stays lazy at its original point after policy-ID checks, preserving
first-error behavior. Request/context/action parsing and both authorization
calls still execute for every row. Changed schema, entities, actions, actors,
malformed input, simultaneous faults, refusal and retry require exact complete
receipt/error parity against the independent original workflow. The candidate
is accepted only after this proof boundary and actual end-to-end measurements.

Then measure typed/borrowed catalog decoding against the existing Value path.
Preserve catalog order, input classification, unknown-entry refusal, policy
source equality and cross-artifact checks. Do not enable borrowed transport or
replace canonical hashing based solely on one microbenchmark. Shared policies
must still complete strict validation before requests are observed.

** Lean and compiler scope

Use the same dependent slot types, Contracts, factory-indexed Session witnesses
and standard-axiom audits. Measure accepted and refused construction separately;
heartbeat counts remain small-allocation counters, not allocated bytes. A
checks-only auxiliary process, if needed, must be labeled startup plus shared
fixture/check work and cannot replace any of the full 81 workload observations.
Avoid new global interning, mutable semantic objects or per-domain wrappers.

Compiler experiments follow ownership/allocation work. [[https://doc.rust-lang.org/cargo/reference/profiles.html][Cargo profile settings]]
belong to the workspace root; evaluate any LTO/codegen change in an isolated
artifact cohort with build latency, size, startup and steady-state execution.
Do not mix profiled/instrumented binaries with ordinary latency or overwrite
the existing qualified default profile. No job-count environment override or
resource/watchdog expansion is part of this plan.

** Final acceptance and stop conditions

Keep the 48 frozen manifest byte identities, 51 catalog entries, 1280 replay
rows, 2560 observed compiled/rendered authorization calls per sample, 23-manifest
original-workflow comparison, 14 handoff scenarios, four Production fixtures,
nine native object families and all type/Contract/axiom/negative-control gates.
Any new cache also needs changed-input, refusal and retry evidence. Resource
records retain executable SHA-256, architecture, exit, bytes units and scope.

Publish one integrated result on the same PR after these workstreams converge.
Report both one-shot process and phase costs using fixed bounded repeated
comparisons, including regressions and variation. Do not declare end-to-end
performance closed from a hot-loop gain or a green correctness job. Cross-host
observations qualify execution separately; their ratios are not speed claims.
