* Common-owner implementation

=Object.compilePrepared= uses the same graph-owned C4 preparation for the root
Plan. Universal =compilePrepared_eq= equates its complete original Plan/error
result. Cedar =Model.compilePlanPrepared_eq= and =Model.compilePrepared_eq=
bind that actual table to the same declarations and unchanged edit/provenance
fold. An active object at its own root still keeps its original Plan. Original
error order and reachable-only validation remain observable. Distinct roots can
still repeat internal ancestor resolution; this is not an ancestor-once algorithm.

=EncodedJson= carries an ordinary rendering thunk and a separate erased
certificate. Array/object closures capture child rendering thunks and keys,
rather than complete semantic containers. Snapshot closures capture their
encoding field; =detach= returns the existing rendering. Generated C confirms
these captures. Actual =JsonEncoding= value/fragment certificates and public
JSON projections remain, with no new trusted axiom.

Pure JSON owners now import the JSON data API. The complete 18-law profile axiom
audit moved to the existing WholeMigration proof owner, with the same namespace,
whitelist and marker. This dependency cleanup does not bypass stock Lean runtime
initialization.

* Initialization and RSS findings

The actual [[https://github.com/leanprover/lean4/blob/v4.34.1/src/initialize/init.cpp][Lean 4.34.1 runtime]] unconditionally calls =initialize_Init=,
=initialize_Std= and =initialize_Lean= from =lean_initialize=. Import narrowing
cannot remove this baseline. The first application-module diagnostic clock starts
after core initialization; it is not a complete runtime timer.

Two native controls have identical main bodies and fixed 50-ms diagnostic
residency, differing only by a =Lean.Data.Json= import. Generated C selects
=lean_initialize_runtime_module= versus =lean_initialize=. Both six-launch
groups return identical bytes and valid PID/exit/clock evidence:

| Control | Image bytes | Median resident MiB during main | Repeated before-main median |
|---------+-------------+---------------------------------+-----------------------------|
| Std clock only | 2599520 | 3.531 | 4.037 ms |
| Same body + JSON import | 103901776 | 35.953 | 23.134 ms |

These are sampled resident observations including code/data, not allocated bytes,
OS high-water RSS or universal bounds. The hold is a diagnostic control only;
business workloads and limits are unchanged.

Twelve separate loader/allocator runs preserve full catalog bytes. Installed
mimalloc 3.4.4 reports 1 GiB reserved virtual arena space, about 35.3 MiB
peak/current committed space and zero purge operations in these short runs,
with process high-water RSS around 50 MiB. Page counts retire while committed
space remains. Reserved, committed, resident and live-object bytes differ.
Generated exports also mark manifest values persistent: a local renderer cannot
retire independently retained global values. Thus ownership improvement need not
reduce RSS. This is not an exclusive byte decomposition or proof against every
possible leak.

All 42 phase/inode diagnostics preserve clocks, exits, full output and observer
shutdown. Reference/final application initialization medians are 45.187/44.565 ms;
main spans are 27.649/27.336 ms and source-ready medians 22.669/22.433 ms. These
small differences do not establish stable end-to-end acceleration.

* Before-main long tail

Fresh Std-only paths observe 716.890/295.160 ms before main; JSON-only paths
observe 2085.574/1237.538 ms. The tail exists without Cedar/C4. Final full-catalog
copies observe 1383.389/1291.387 ms on first paths versus a 66.695-ms repeated
median. Same-inode/new-path controls remain separate; this is not proof of a
pure pathname cause.

The owned stderr reader retains raw offsets and line-arrival clocks. In the
first final loader/allocator run it is ready at 9.610 ms; the first loader line
arrives at 1186.561 ms and the first initializer line at 1188.710 ms. Main-entry
observer lag is 0.035 ms. These are arrival upper bounds, not syscall durations.

One fixed owned-PID sample per Lean/Rust role obtains 86/68 frames at
=_dyld_start + 0=. Tool duration is separate from its one-second request; sampler
completion is not native child-exit time. PID, protocol, output and clock evidence
bind the owned invocation. Paths are privacy-redacted and binary image lists are
unavailable, so sampled image UUID verification is unavailable. These observations
locate the wait around the OS/initial loader-entry boundary described by
[[https://github.com/apple-oss-distributions/dyld/blob/main/dyld/dyldStartup.s][Apple's entry assembly]], rather than a C4/serializer stack. They do not identify
an exclusive kernel, security-service or page-in callback. Python xattr APIs are
also unavailable on this Darwin build; that field is not an empty successful read.
