* Design objective

Provide a typed Cedar capability family whose operations can be assembled,
selected, prepared and consumed using existing LeanPOO Functional APIs. Industry
objects contribute settings, predicates and required capabilities. Complex Cases
compose those objects and capabilities against one explicit current context.
The existing Cedar functions and their correctness witnesses remain the semantic
implementation of each capability.

The resulting path is:

#+begin_example
typed industry objects + Contract refinements
  -> C4-selected capability factories
  -> Requirements.prepare / prepareWith (resolve required capabilities once)
  -> compile -> validate -> checked policies
                           |-> encode / publish
                           `-> evaluate actual request and entity snapshot
  -> current Host admission -> business effect
#+end_example

Plain Cedar records continue to serve as wire values, schema inputs and exact
semantic projections. Typed objects own construction and inheritance; prepared
functions own reusable workflows; proof-indexed values carry admission evidence.

* Capability and context design

** Separate reusable policy inputs from changing request inputs

Define a policy context containing the actual model/source, selected root and
schema. A request context supplies the actual request and entities; a separate
Host admission context supplies the actual immutable effect/scope and revisions.
Factories close over only the context they really depend upon.

Do not cache compilation under a context that also changes on every request.
Do not retain authorization under only a root name, profile name or digest.
Model, schema, request and Host evidence identities must remain explicit in the
relevant result type or verified binding.

** A finite, heterogeneous capability key

The initial capability inventory is compile, validate, encode/publish and
authorize. Later add review/analyze and Host-bound preparation as their consumers
migrate. Use a Lean inductive key and a dependent =Value context key= family,
with =Factory= and =Provider= from LeanPOO; avoid a String-to-Any method table.

Capabilities representing a later stage return functions taking the earlier
stage's typed result. For example, a validator consumes an exact compiled result,
and an encoder consumes an exact checked result. This makes shared intermediate
work explicit instead of letting each capability independently recompile the
same root. Errors retain the existing typed Cedar/SPEC causes and stage order.

The following are conceptual result indices, not new implemented APIs:

#+begin_example
Compiled policyContext
  carries policies and model.compile root = .ok policies

Checked compiled
  carries actual schema/policy validation evidence for compiled.policies

Published checked
  carries exact serialization and unique-policy-ID evidence

Authorized checked requestContext
  carries the actual Cedar response and its evaluation equality
#+end_example

Reuse existing =PolicyJson.Publication=, =CompoundAuthorization.Receipt=,
=LayerReceipt= and policy proof bundles wherever their indices already match.
Avoid keeping parallel old/new receipt structures with identical information.

** Prepare the family before repeated consumption

As in LeanPOO's ContextualFactories/DictionaryConsumers examples, C4 assembles
the contributed provider family. A Case declares only its required capability
keys; =Requirements.prepare= resolves those keys once and retains an ordered,
heterogeneous factory tuple. Missing capability errors must name the key.

=Requirements.Certified= and =CertifiedConsumer= are appropriate when the joint
claim has a concrete proof over all required data. An arbitrary predicate or
opaque function is not automatically a certified capability. A provider offering
a checked validator/authorizer must produce the actual Cedar witnesses required
by its result type; a Boolean override cannot manufacture those witnesses.

* Important constraints discovered in the source

** Dynamic type metadata needs a Cedar interpretation

Static Lean types already protect dependent capability results. Dynamic plugin
or configuration descriptors may additionally use PrototypeTypes and its bounded
inference/interpretation APIs. Their scalar, container, function and refinement
meanings must be connected to the actual Cedar values and callback interface.
An unresolved constraint is not a successful type check. Metadata validation
cannot replace Cedar's own schema validation or justify erasing its error cases.

** Publication order is observable

=PolicyJson.publish= currently executes compile, schema-definition validation,
schema well-formedness, policy validation, export, then duplicate-ID admission.
The refactor must preserve the exact first failure and ordered policy material.
Compile-only/evaluation APIs must retain their documented weaker boundary; route
deployment consumers through an explicitly checked publication operation.

** Partial JSON export is not yet a round-trip Codec

=PolicyJson= contains bounded/partial AST and value exporters. A =Codec= requires
a proved decoder/encoder law. Initially compose these exporters as typed
Except-returning factories. Introduce a lawful codec only for a supported,
explicitly refined domain with a real decoder and proof. Existing JSON fields,
IDs, ordering and Rust Cedar parser admission remain authoritative.

** Reuse requires actual identity evidence

=Model= contains cached functions/objects, and schema comparison already has its
own semantics. Do not assume a global DecidableEq over an opaque model or treat
a version/digest match as equality. Start with preparation scoped to a captured
immutable source/schema; add ContextSlot only when the selected context really
has decidable equality or an existing proved reindex/rebind law. A cache hit
reuses dependency data, not a final request authorization or current Host grant.

** Ordered policies and errors survive table abstraction

Policy validation currently compares entire bodies and preserves the first
error; policy modules separately enforce edit ownership and order. TableRevision
does not justify reducing equality to PolicyID or using an unordered map as the
published policy list. Keep the indexed Cedar fast path until its replacement
has semantic and resource evidence.

** Functional combinators preserve authorization boundaries

Factory.recover is appropriate for explicitly specified recovery behavior. It
must not translate a missing capability, failed contract, solver unknown,
revoked grant or stale publication into an allow. Method combinations select
construction/check behavior; Cedar still owns permit/forbid aggregation.

This order supplies shared capability operations before broadly rewriting the
large Examples. Receipt unification and removal of the replaced functions belong
to each slice's exit criteria; keep a working consumer while moving ownership.

B1 and B2 implement the typed result stages, C4-selected operations,
=CertifiedConsumer= method contract, retained root preparation, delayed export,
actual-request authorization and both Case export paths. Their tests include
universal publication/error equality and complete compressed-manifest equality.
C1 additionally migrates AttestedDataAccess revision export, GoogleThreat stage
authorization/export, and DataFlow multi-root authorization/export. It reuses
LayerReceipt, proves singleton-response alignment and ordered batch composition,
and removes the duplicate singleton export dispatcher. Independent previous
export algorithms, full response/policy projections, malformed/reordered/repeated
layers, changed schema and removed sources provide regression gates. Domain
revision/delta/BoundOperation operations retain their own stronger or weaker
contracts; C2/D are not advanced by these receipts.

* Cross-cutting acceptance matrix

- Exact old/new success values, Cedar policies, policy order and serialized bytes.
- Exact first error on multi-failure inputs; distinct deny, evaluator error,
  missing capability, incomplete analysis and stale scope outcomes.
- Same body with a different ID, same ID with a different body, reordered bodies,
  duplicate IDs, tombstones and competing owners.
- Independent schema, root, factory family, request, entity, source, epoch and
  effect changes must invalidate only their actual dependent preparation.
- A refined child cannot weaken inherited Contract refusal; raw object reads
  cannot become an authorization/admission path.
- No delivery on rejected prepare/redeem; actual final Host revisions and effect
  identity are checked at the existing point of release.
- Library and Production imports stay independent of Examples and Tests.
- Kernel proofs and exact-head CI remain separate evidence from Case simulation,
  downstream Rust execution, resource counts and elapsed-time measurements.
