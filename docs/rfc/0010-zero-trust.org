#+TITLE: RFC 0010: Research-Aligned Zero Trust Effect Boundary
#+LANGUAGE: en

* Status and decision

The Lean API is a candidate reusable functional framework in SPEC, not a certification of a
deployed Gateway. Applications enrich it with concrete identity, persistence,
budget/history and effect-boundary implementations. Review the research basis
before treating an interface name or a passing example as a security claim.
The engineering sequence follows [[file:0004-authorization-delta.org][Authorization Delta]]:
research question, precise model, explicit premises, proof/counterexample,
public API, then implementation refinement. Preserve the distinction between
a theorem, a solver report, a finite test and an unimplemented Host obligation.

* Integrated current-release binding

The [[file:../zero-trust-contract.org][current-release coherence implementation]] makes the active release an
independent mandatory input to ongoing Gateway admission. A valid old receipt
can coexist with a changed active root; the new binding joins current compiled
policies, root, enforcing mode and epoch to the current request and entities.
Production medical/financial POO profiles and independent strict-schema Rust
replay exercise the composition through the existing Zero Trust CI module.
This discharges a local safety obligation, not all architecture, temporal or
trajectory guarantees in the source table above.

* Architecture completeness review

The predicate conjunction is an effect-boundary kernel. It is insufficient as a
complete Zero Trust architecture without identity, resource inventory, protected
communications, dynamic Policy administration, posture monitoring, authenticated
fact sources and feedback. A consumer cannot discharge these responsibilities
by providing predicates that always return True.

The seven-tenet alignment to NIST SP 800-207 is an architectural checklist:
all services/data are resources; communications are protected independently of
location; grants are scoped to sessions/resources; decisions use dynamic facts;
resource posture is measured; authentication/authorization precede access and
are reevaluated; security observations inform governed improvements. These
tenets are not seven properties established by the current Lean code.

| Logical role | Framework interpretation | Application evidence required |
|--------------+--------------------------+-------------------------------|
| Policy engine | Authorization decision over authenticated subject, resource, right and current context | Concrete Cedar projection and validated source facts |
| Policy administrator | Establish/revoke the admitted path using the engine decision | Bound publication/activation, credential custody and revocation ordering |
| Policy enforcement point | Admit, monitor and terminate effects at the real use boundary | Complete mediation, current-state join and exclusive execution capability |
| Identity / posture / resource sources | Provenance-bound, versioned evidence interpreted by requirements | Attestation, expiry, trust-domain binding, redaction and source availability semantics |
| Monitoring and audit | Observations and outcomes inform later governed decisions | Durable records, privacy and a controlled path back to Policy publication |

Roles are independent of programming languages and may be colocated. Protected
networking alone does not imply application authorization. Resource ownership,
cluster membership and shared workload identity do not establish an actor's
incarnation or delegation rights. The core remains independent of Gateway.

Public reference interfaces clarify concrete missing obligations:
[[https://github.com/spiffe/spiffe/blob/main/standards/SPIFFE_Workload_API.md][SPIFFE's Workload API]]
requires caller identification and complete update/redaction handling; a
reconnected stream does not preserve removed identity material. The
[[https://github.com/spiffe/spire/blob/main/doc/plugin_agent_workloadattestor_k8s.md][SPIRE Kubernetes attestor]]
documents that its selectors do not resist a compromised node. The
[[https://github.com/openziti/ziti][OpenZiti architecture]] illustrates service-level
connectivity authorization and encrypted networking. None is a checked dependency
or a proof of application consumption, budgets or recovery. They motivate
consumer identity/channel requirements; this library does not implement them.

=ZeroTrust.UsageControl= now distinguishes initial/ongoing authorization,
environmental conditions, obligation actions across actual before/after states,
and allowed mutations. It retains =Framework.required= at every new effect.
The application's existing transition relation is reused. =resume= means only
that its recovery relation holds; it cannot authorize a new effect. =close=
requires terminal and accounted evidence, and cannot release unknown exposure
from a terminal label alone. Post-use accounting is an application extension;
the library does not claim UCON's full temporal rule system, fairness or eventual
obligation fulfillment. This addition uses no Gateway types or new scheduler.

The application must materialize a current context containing authoritative
subject/delegation, resource/right, Policy/profile, posture, budget/history and
execution-owner evidence. Evidence needs producer authority, meaning/schema,
source cut and validity. The deciding transition must order relevant changes
against use. A lease only bounds staleness unless the source protocol provides
stronger ordering; unavailable sources do not imply healthy/current.

Authorization Delta review must identify the exact authoritative parent and
candidate in that context. Existing LeanPoo EvidenceBinding preserves the
original invocation rule while binding subject/descriptor/context references.
Reference equality does not authenticate the producer or implement final CAS.
The required parent must be selected independently of the child. In particular,
the review API now prevents ordinary record construction/update that splices
analysis and snapshot fields. This does not authenticate deserialized artifacts
or prove solver results. =Gateway.PublicationReview= composes actual LeanPoo
evidence-bound invocation with current ZeroTrust guards and the Host commit
relation. The adapter's exact-result checks are distinct from native durability
and atomic publication admission, which remain implementation obligations.
The application adapter additionally distinguishes approved lookup from durable
registration, recovered projection and current registrar incarnation. A stale
worker cannot acquire a current final witness from a historical matching artifact.
The native Host must join the independent registration commitment, actor and
epoch with final publication under one authority decision; local readiness is
not anti-rollback evidence. Model laws do not revoke a real transport credential.
The adapter's single =RegistrarAuthority.admitted= meaning binds the complete
credential and exact command possession. Its command-indexed hook retains
ZeroTrust and original Contract requirements. Concurrent/fault models consume
qualified references; they do not define another identity policy evaluator.
Pending results and lost replies must reconcile the original intent, not replace
the evidence, rebase the parent or clear unresolved consumption.

* Functional model and POO interpretation

=Requirement Effect View= is a typed predicate function. =Framework.required=
conjoins authenticated identity, authorization, current-at-use observation,
committed consumption, unknown-exposure retention, non-revocation and mediation.
=adapt= projects application effect/view types; =strengthen= and
=Framework.withRequirement= preserve original requirements by implication.
These are pure framework functions, not a new Policy language or Cedar evaluator.

=ZeroTrust.ProfileObject= reuses =LeanPoo.Object.Dataflow.define/extendWith=,
inherited field extension, =Functional.ObjectProfile= Contract and the actual
factory-indexed Session. A selected profile carries a typed proof that its
requirement refines the original function. Adding a child requirement preserves
that original requirement. The original is a type index, not an overridable
field; choosing which original is authoritative remains a Host obligation.
Objects and inheritance interpret the generic functions. They do not put a
Gateway operation, provider, protocol or account into the core.

The root index alone does not retain every extra parent condition under raw
overrides. The executable POO counterexample admits a root-only override of a
stronger parent. =composeSessions= therefore retains the independently required
parent and selected Sessions; =Composed.requirement= conjoins their actual reads.
Gateway's =fromFrameworkObject= requires both. Its proof preserves parent
requirements and the original Gateway Contract. The publisher must still bind
the required parent's full source/Contract independently of the child request.

* Continuity, mutable attributes and revocation

The selected fragment formalizes checks at each new effect boundary.
=Observation= binds attributes and an authoritative generation.
=atObservation= adds equality against the actual observation at use. Restoring
equal attribute values in a later generation does not revive an old observation.
No generation non-reuse or independent persistence implementation is inferred:
the application must establish the reader's authority and monotonic recovery.

=MediatedStep framework step before effect after= wraps the application's
existing transition relation. Every =some effect= transition must satisfy the
framework against its actual pre-state. A =none= transition can represent fact
changes, recovery, observation or previously admitted buffer drain. =Run= composes
arbitrary finite checked histories; =run_preserves= projects any invariant whose
step-preservation law the application has already proved. It is not a second
runtime state machine or a proof that every native IO is correctly labelled.

The checked laws include =effect_step_rechecks=, =revoked_state_cannot_emit=,
=changed_generation_blocks= and strengthening/refinement composition.
These express a finite safety fragment motivated by UCON continuity/mutability;
they do not translate its entire temporal rule system, establish fairness or
guarantee eventual post-use updates. Revocation blocks new admissions after its
authoritative ordering point. It cannot recall already admitted bytes.

* Gateway consumption of the frameworks

=CedarPooSpec.Gateway.ZeroTrust= owns the former application-specific Host,
publication-indexed Proposal and FinalUse. Its =framework= and =specialize=
functions interpret the generic requirements through existing POO publication,
Cedar admission and consumption laws. =final_use_satisfies_framework= and
=specialization_preserves_core_and_original= retain both the generic conditions
and the actual original profile Contract. These immutable proofs are duplicable;
they are not affine send capabilities.

The initial =FinalUse= binds one captured admission pre-state. It is not a
per-row root-consumption API. =continuing= instead keeps the original scope and
consumption while requiring a fresh assessment at the current state.
=CommittedPrefix= explicitly requires the current authoritative operation
history to contain the installed consumption plus later history.
=committed_prefix_rejects_reconsumption= rejects a renewed authority against
that actual recovered ledger. A Host Boolean called committed alone is
insufficient. The adapter does not prove that its assessment corresponds to
real immutable Cedar facts or that its prefix witness is recoverable from disk.

Authorization Delta still compares policy roots in the same validated world,
under existing exact-query/schema/UNSAT premises. It does not prove safety across
changing entities, agent choices, budgets or histories. Combining it with Zero
Trust does not remove those premises or turn a solver report into a Lean proof.

** One control loop, two semantic comparisons

At publication, compare the independently selected active parent with the
candidate under the exact schema and policy sources. Review decision gain/loss,
error-free execution gain/loss, and required reason/provenance changes separately.
At each effect, evaluate current authenticated facts and requirements under the
actually active publication, then join that admission with committed original
consumption, outstanding exposure and the final mediation transition.

#+begin_example
independent active parent + candidate + schema/source binding
  -> Delta analysis and original Contract review
  -> governed publication (current parent/epoch/mode; atomic Host commit)
  -> current identity/facts + actual request + active publication
  -> error-free Cedar admission + current Zero Trust requirements
  -> committed consumption / unknown holds + final effect boundary
  -> witnessed outcome / mutation / recovery -> next current assessment
#+end_example

This is a proposed integration flow, not an extracted theorem graph. Delta is
an input to governed policy change; it is not a cached permission to use a
resource. Zero Trust does not require every legitimate change to be no-gain.
A financial unfreeze, consent grant or delegation extension may intentionally
gain access and needs independently authorized, precisely bound review. Existing
=advanceNoGain= remains the restriction/equivalence path; it must not silently
be reused as an approved-expansion path. Unknown/error/incomplete analysis is
neither no-gain nor approval.

Let =Exec(P,w)= mean error-free Cedar Allow in one validated world. The existing
no-expansion theorem proves =Exec(after,w) -> Exec(before,w)=. It does not prove
=Exec(after,w_new) -> Exec(before,w_old)=. RFC 0004's existing 2-by-2 trace table
holds policy or input fixed to expose this distinction; its diagonal alone
cannot establish causation or safety of an alternate trajectory. Fact-source,
projection or schema changes must be identified explicitly and revalidated.
Cross-schema safety requires a separately specified relation between worlds.

The ongoing proof target is: accepted current assessment implies error-free
Allow for its exact current request/entities and active policies; if a bound
no-gain proof applies to that same validated world, it also implies baseline
execution there. At the same time the original operation remains consumed and
unknown exposure remains retained. A separate governed-gain path retains all
current-use and consumption requirements without asserting baseline implication.
These are proposed targets, not declarations already implemented in Lean.

For histories, prove preservation of an explicitly defined application invariant
under policy publication, fact updates, effect commits and recovery. Required
components include scope continuity, retained consumption, retained unresolved
exposure, and no new mediated effect after an ordered revocation. Each component
needs a step law, including the non-effect transitions. This is an inductive
safety goal; it establishes neither liveness nor the delegated-agent paper's
expected-utility guarantee. Already admitted bytes are outside a retroactive
revocation claim.

** Terminal revocation across maintenance histories

The UCON continuity requirement motivates testing the effect boundary after
each change of authority. The current simulator represents terminal revocation
for one original operation. Its maintenance trace includes monotone clock
updates, fact renewal, source invalidation and observed settlement.
=Gateway.Lifecycle.revoked_trace_blocks_use_and_publication= proves by induction
that any finite maintenance suffix preserves refusal by both the current-use
guard and the reviewed publication guard. The theorem quantifies over every
handle and envelope, including a fresh one. =burned_trace_stays_burned= shows
that the same suffix preserves recorded consumption.

The publication result applies to the guard used by =publicationContract=.
Rust also exercises the concrete publication path with a ticket issued before
revocation and checks that refusal leaves the epoch and history length intact.
The existing recovery control checks that renewal and mediator replacement
preserve revocation even when the current Cedar evaluation allows the request.
These are safety results for the modeled simulator transitions. The trace
takes observed settlement as an input. The recovery Contract and native
independent verification govern how that input is obtained.

Gray and Lamport's [[https://arxiv.org/abs/cs/0408036][Consensus on Transaction Commit]]
provides a separate comparison for distributed recovery. The simulator's
surviving owner and independently signed outcome are explicit premises.
A distributed Host would require a separate agreement and durability model
before this result could cover concurrent writers across failures.

** Distributed writer and recovery boundaries

A signature authenticates the writer's bytes. If two processes can use the
same witness key, two signed histories can have the same length and disagree
at the same position. The audit authority may now supply an independently
retained signed checkpoint through =independent_checkpoint= in the trust
configuration. The runtime verifies that checkpoint against the configured
witness key, then requires the authenticated candidate history to extend the
pinned boundary. Recovery also checks its surviving local frontier. A pin must
come from a durable authority independent of the candidate. Selecting a pin
from the history being audited gives no independent fork protection.

=Lifecycle.historyContract= binds both frontiers to the same checked history.
=history_invocation_extends_independent= extracts the independent extension
from a successful invocation. =same_length_fork_refused= checks that signature
validity and equal length cannot override a different boundary. The Rust
control constructs two valid chains with the same signer and height, confirms
the old floor alone admits both, then exercises independent audit and recovery
refusal as well as acceptance of a proper extension.

Three separate obligations remain at the distributed Host boundary.

| Boundary | Required Host premise | Failure when absent |
|----------+-----------------------+---------------------|
| Committed history | One authenticated committed prefix per authority and configuration, with a durable checkpoint reader that does not roll back. Raft's leader completeness and membership-change protocol are reference mechanisms for a crash-fault deployment. | Two writers can certify different state at the same position, or recovery can reopen a retired cut. |
| Revocation and Delta publication | Order both in the same authority and enforce the authenticated current cut at the final resource or publication receiver. Chubby's sequencer puts the check at the recipient. | A delayed writer can act after revocation even when its earlier local check passed. |
| Independent effect recovery | Verify the retained intent and a provider outcome under independent keys and retain quarantine while the outcome remains unresolved. | Agreement about the intent log alone cannot establish whether external IO took place. |

The existing =PublicationReview.Final= binds the original review and the
current registrar, cut and Host commit relation. The finite revocation trace
covers the modeled maintenance transitions. A replicated deployment still
needs to establish the premises of both results: configuration transitions,
durable non-reuse of cuts, and receiver-side fencing ordered with each actual
write. An independent checkpoint detects a divergent presented history.
Quorum agreement and external effect settlement require their own witnesses.

Sources: [[https://www.usenix.org/conference/atc14/technical-sessions/presentation/ongaro][Ongaro and Ousterhout, Raft]],
[[https://research.google.com/archive/chubby-osdi06.pdf][Burrows, Chubby, Section 2.4]],
and [[https://arxiv.org/abs/cs/0408036][Gray and Lamport, Consensus on Transaction Commit]].

** Receiver ordering and independent checkpoint custody

=Lifecycle.receiverPublicationContract= refines the actual reviewed publication
Contract with the receiver's current owner and generation. The release result
still comes from the original Delta invocation. The Lean proofs reject a
retired ticket even if the reviewed policy and source bytes remain equal, and
reject publication after revocation even with a fresh cut. Revocation advances
the same cut used by publication. In the Rust simulator, the final receiver
checks the private ticket, the current guards and the release under the same
deciding lock used by revocation. The replay covers both commit orders and a
two-thread race. If publication wins, the committed epoch remains visible
after revocation. If revocation wins, the old ticket cannot install a release.

The Unix =CheckpointStore= is a local adapter for the independent history
Contract. An operator bootstraps it with a trusted signed checkpoint in a
separate trusted directory. Recovery uses =load= to obtain the typed pin for
=AuditAuthority.independent_frontier=. =advance= takes the writer lock before
reading that pin and verifies that the complete signed candidate chain extends
it. Persistence stages the signed checkpoint, synchronizes its bytes, replaces
the live name atomically and synchronizes the directory before reporting
success. Reopening the store must use the existing pin. Missing or invalid
state fails closed. Errors after replacement require rereading the store
because the replacement might already be visible.

The file adapter assumes a trusted, non-rollback local filesystem and stable
lock-file identity. The test races two same-key, same-height writers and
reopens the store to verify that only the winning prefix survives, a proper
extension advances it, and a corrupt pin cannot be replaced from candidate
data. Reopening exercises custody across handle restart. Power-loss behavior
and remote storage semantics require separate qualification.

A replicated Host must serialize receiver fencing with the actual publication
or effect write, using the authenticated current authority cut. A receiver
that only remembers its latest observed cut cannot detect a revocation it
has yet to observe. Chubby's receiver-side sequencer check motivates the
boundary. Raft's committed-log properties explain the separate premise that
an independent durable pin represents one committed history across replica
failover. The local lock and file adapter establish neither replicated
consensus nor external effect settlement.

required-profile refinement. =current_admission_has_error_free_allow= retains
the canonical operation and current error-free decision, including governed

world, AdmissionBinding and ExactCoverage with original consumption and unknown
retention. The changed-fact fixture proves that an old receipt cannot provide
this current assessment, and that the current deny world has no such assessment.
No solver-report-to-ExactCoverage conversion or new authorization evaluator is
introduced. In particular, the current four-root Release analyzer classifies
Cedar decisions, not exact error-free execution coverage. Publication review
does not establish the ongoing Delta theorem without its additional explicit
ExactCoverage premise. Actual current-use admission still rejects evaluation
errors. Core ZeroTrust still imports no Gateway.

The existing Gateway test owner reuses released LeanPoo =PropertyTesting.samples=,

Cartesian/sequence coverage, not a statistical claim about random sampling:
384 release configurations and 1,372 complete three-command histories over seven
commands. All 4,116 transition replies and full post-states are compared with an
independent test-only Rust store interpreter. Actual analyzer results supply the
no-gain/gain classifications; those reports remain external-solver evidence.
Ten Functional-produced Cedar policy/current-fact cases are independently replayed
by the official Rust authorizer. The full catalog acceptance additionally retains
all 51 entries, frozen artifacts, native/interpreted equality and original
uncached Rust workflow comparisons.

Simulated recovery retains the authority's durable active image, independent
epoch floor and unresolved result flag. Live rollback cannot revive a consumed
review; lost replies remain unresolved through recovery. A deliberate control
which also rewinds the authority floor can commit twice. This states the precise
source-authority assumption, not a proof of rollback-resistant native storage.
The model covers publication histories and current Cedar inputs; full application
transition refinement, real credential custody, provider IO, settlement and
unbounded fairness remain outside this bounded acceptance. Generic per-use
requirements and existing consumption laws are retained rather than replaced
with new domain-specific ledgers.

ignored Lake build directory. Final source and remote CI qualification must be
reported separately from this design/implementation inventory.

** General publication laws and finite-history induction

The follow-up strengthens the proof coverage without changing the release or
simulation algorithms. =ReviewSnapshot.currentPolicies_epoch= exposes the epoch
check in actual successful revalidation. =advanceReviewed_postcondition= proves
that every successful no-gain or governed-gain advance matches that review epoch
and installs exactly the returned policies/root in enforcing mode at the next
natural epoch. =stale_epoch_cannot_advance= and
=returned_state_rejects_republication= refuse reuse of that review under arbitrary
later approval callbacks, models and schemas. The guarantee is about the actual
returned state, not about a caller supplying an older state again.

=PublicationReview.delta_final_retires_resolved_review= connects these laws to
the actual Final receipt, selected artifact, resolved review and committed
post-state. Original Contract, registration, fencing and current-use premises
remain unchanged. The proof supplies neither an affine IO capability nor atomic
arbitration between two callers holding the same pre-state.

The existing test-owned =publicationStep= now has a checked step invariant:
the independent epoch floor never decreases, a successful commit advances the
matched review epoch, and unknown results remain retained. Induction directly
over released LeanPoo =traceObservations= proves, for arbitrary finite command
lists interpreted by that function, that the same fixed review commits at most
once, and that every later observation retains an already unknown result.
These proofs have no three-step horizon or sample-count premise. No second
runner or runtime state machine is introduced. The seven declared commands,
fixed reviewed artifact and preserved independent authority floor delimit the
model; exchanging artifacts or rewinding that authority is a different model.

The 384 configuration checks and 1,372 three-command Lean/Rust histories remain
unchanged as executable conformance evidence. The pure-model induction does not
extend the Rust comparison to unbounded executions or machine-word overflow,
and establishes no deployed storage/IO refinement, fair scheduling or MDP utility
guarantee. Existing floor-rewind and concurrent-pre-state counterexamples remain
valid outside the strengthened forward-history premises. All new lifecycle and
history proofs are kernel-checked using ordinary logical axioms; they consume no
new native-decision axiom or external UNSAT certificate.

The standalone current-admission consequence no longer requires unused =BEq E=
or =LawfulBEq E= instances. Consumption still requires its actual lawful effect
comparator. This removes an irrelevant API prerequisite without changing
admission, equality or runtime execution.

** Observation-cut compare-and-advance and native arbitration

=ZeroTrust.Observation.compareAndAdvance= is a pure specification for an
optimistic preparation followed by an authority-owned current transition. It
compares the captured generation first, passes the actual attributes to the
checked transition, preserves a fresh transition's original error, and advances
the observation generation only on success. The successful-transition theorem
retains its exact input/output and successor generation. The returned-cut law
rejects an old generation under arbitrary later callbacks, including when the
attribute values have been restored. The framework composition theorem retains
the existing MediatedStep requirements; matching a cut is not authorization.

The observation cut is independent of the policy epoch. Every participating
posture/configuration/recovery writer must advance the same authority cut,
even when it restores equal attributes or does not publish a policy. Generation
values are scoped to that authority and require authenticated, non-reused
interpretation. Two pure evaluations against copies of the same pre-state can
still both succeed. The primitive performs no IO and makes no atomicity claim.
The native adapter must linearize read, compare, current admission, installation
and the local commit observer under one actual authority boundary.

The test-owned Rust authority now supplies that boundary using one shared mutex
for publication and control writers. Two real threads capture before a barrier
and race to commit; only one eligible callback observes installation. A second
native writer demonstrably cannot acquire the boundary while the final observer
runs. Ticket ownership uses an allocation-owned Arc identity, so equal generation
numbers from another authority are refused. This is process-local ownership,
not a workload credential, signature or persistent identity scheme.

The existing release interpreter is reused; no new Cedar evaluator, production
Gateway crate, backend provider or database is introduced. The Rust fixture code
moves from SDK preparation tests to the explicit =publication_review= test owner.
The existing 1,372 histories and ten Cedar replay cases remain intact. A companion
Lean producer invokes the actual compare-and-advance primitive for 2,528 prepared
histories / 12,528 steps: all six legal two-actor prepare/commit interleavings,
both actors' lost-reply choices, every insertion boundary for recovery, live
rollback and mode updates, plus old-cut and freshly recaptured ABA histories.
The native authority compares every reply, complete modeled state, prepared cuts
and actual observer invocation count with those Lean observations.

Eight additional native controls cover eligible/refused thread races, ABA,
lost-reply recovery, machine-counter exhaustion, a competing writer, foreign
ownership and two intentional counterexamples. Independent prechecks can admit
two callbacks; rolling back the whole authority record can revive an old ticket.
Both counterexamples remain green diagnostics of absent premises, not admitted
behaviors. Native generation exhaustion uses checked addition and refuses before
installation/observation. The finite native fixture range and that explicit
word-boundary refusal do not establish unbounded machine arithmetic refinement.

The tests model logical recovery while the authority record survives. They do
not implement process-crash durability, cryptographic custody, physical rollback
resistance, remote delivery, fairness or a production mutex architecture. Other
Host implementations may use a transactional CAS with the same ordering; the
source reader, all relevant writers and the final use boundary must participate.
Generated CAS fixtures stay in the ignored Lake build directory. Lean/Rust own
all semantic assertions; Python remains unchanged process/artifact glue.

** Prepared-history induction and persistent retirement

The finite interleaving corpus is accompanied by kernel induction over the
actual =publicationScheduleStep= function and the released POO
=traceObservations= projection. For every finite command list, with arbitrary
initial schedule, captured tickets and fixed reviewed artifact/approval/fault
choice, the proofs establish at most one successful publication and retention of
an already unknown result. Preparation, missing/stale/denied commits, recovery,
live-image rollback and mode changes all participate in the proof. There is no
five-command horizon or legal actor-order premise; the model still has its two
caller slots and one fixed review. This does not prove arbitrary artifact
replacement or unbounded native machine-word refinement.

The step proof derives generation/floor monotonicity from the actual
compare-and-advance and release postconditions. Induction proves that a retired
cut remains refused at every later observation, for arbitrary checked callbacks,
even after equal attributes are restored. Independently, the public
=run_generation_monotone= and =Observation.retired_cut_refuses_after_run= laws
reuse the existing application =Run= relation. Their premise explicitly covers
every writer, including no-effect recovery edges; mediation alone does not
imply monotonic recovery. A Lean counterexample retains a mediated rollback edge
that revives the cut when that premise is removed.

The native fixture interpreter checks monotone generations/floors, unknown
retention and stale-ticket state/observer preservation against its actual shared
authority, separately from complete Lean JSON equality. The original fixtures,
counts and negative controls remain intact. These are functional safety proofs
and conformance checks, not fairness, persistence or performance claims.

** Review replacement and consecutive publications

The same test-owned native authority now keeps its registered reviewed artifact
inside the current-state mutex. Registration checks generation exhaustion,
installs the selected immutable review and advances the same cut without
changing the release image or clearing unknown results. Equal-artifact
re-registration also advances the cut. A real competing registrar cannot write
while the final commit observer holds that boundary. No registration credential,
durable registry or new production provider is implemented here.

The actual four-root analyzer supplies three reviews: an epoch-seven governed

candidate and their actual C4 merge; it does not fake four roots with the same
name. Its three new roots also pass six original Functional/Cedar SDK Case

choices, registration ABA, stale retries, recovery, rollback and two legitimate

per-review observer counts agree with Rust. The earlier fixture bytes stay
unchanged. The finite two-epoch corpus is conformance evidence, not a universal
two-publication limit or a general registry protocol.

=delta_final_rejects_resolved_review_after_run= extends the actual Final's
resolved-review retirement across later application runs, which may use other
reviews or approvals. Its strengthened Final binds the post-commit independent
frontier to the installed epoch. Remaining premises preserve the frontier for
every later writer and require freshness before the later raw Delta check.
A restored live image can rewind; that is why this law uses an independent
frontier rather than assuming the live epoch is monotone. The companion
registration scheduler has a kernel step law and arbitrary-finite-history
induction retaining both frontiers and unknown results, for arbitrary selected
reviews and both publication models. The current floor guard remains mandatory.

The native tests retain an unfenced replacement counterexample: if a writer

** OAuth evidence at the Gateway resource boundary

=Gateway.OAuth= is a sender-constrained resource-side profile. Its Contract
binds an authenticated, active grant to the issuer, subject, client, resource
audience, required scopes and time of the actual use. The Gateway selects
the expected identity and required scopes independently of the token claims.
The resulting OAuth requirement strengthens existing Cedar and Zero Trust
checks. It cannot waive effect authorization, consumption or final mediation.

The Host verifies token bytes and current grant status, including revocation
according to its issuer profile. JWT verification or authenticated token
introspection must supply these facts. DPoP uses verified proof bytes, the
effective request method and RFC-normalized target URI, token hash, key
thumbprint, freshness, applicable nonce validation and a committed replay
reservation. The Host owns the replay policy and storage. DPoP URI binding
does not bind query parameters or request content. The original Gateway
Contract still binds the exact effect. Mutual TLS uses the certificate
thumbprint of the authenticated request connection. An unauthenticated
forwarded certificate header cannot provide that observation.

The proof is conditional on these Host observations. The model has no
authorization server, token parser, signature verifier, TLS terminator or
distributed replay store. A deployment must bind the authenticated evidence
to the same deciding view used by the Gateway. AgentCore and FHIR expose the same strengthening over their resource
policies. FHIR patient, session and inactivity checks remain in its base
policy. AgentCore retains its principal and action restrictions.

The Rust Gateway accepts the trusted current-use projection at its OAuth
boundary. One shared process-local replay guard admits at most one use of
an issuer, proof key and proof ID. A deployment must supply bounded replay
retention and a shared atomic reservation across processes and restarts.
The native controls race two applicable routes, reject a replaced peer
certificate, and deny a fresh proof after revocation. Each use requires
fresh grant status. The adapter must obtain it under the same authority
boundary as final effect admission. This repository does not contain the
deployed OAuth verifier or a production shared replay store.

The upstream Lean =Authority= owns the active grant inventory, revoked token
identities, current clock and replay reservations. =commitContract= binds the
exact successor for one verified attempt. The proof key joins issuer, sender
key thumbprint and proof ID across routes served by the same authority. An
attempt cannot supply its own active status or install a reservation by
setting a flag. A successful commit makes another attempt using the same
proof key inadmissible. Revocation refuses the token on every later use,
including with a fresh proof or the original authenticated TLS certificate.

This is a pure library transition. A downstream Gateway must serialize it
against the actual current authority and combine it with Cedar authorization
and final effect admission. Two evaluations against independent copies of
the same pre-state can both succeed. The contract therefore does not claim
cross-worker atomicity without a shared deciding store.

*** Research basis and proof boundary

OAuth contributes delegated authority scoped to a resource. The Zero Trust
policy still evaluates the actual use with current evidence, applies the
resource's own authorization policy and mediates the resulting effect.
An earlier grant does not establish current permission. This separation
follows the resource-centered architecture in
[[https://csrc.nist.gov/pubs/sp/800/207/final][NIST SP 800-207]].

|--------+------------------------------------+---------------------|
| [[https://arxiv.org/abs/1601.01229][Fett, Küsters and Schmitz, A Comprehensive Formal Security Analysis of OAuth 2.0]] | Separate authorization, authentication and session integrity. Treat the configured issuer and verified grant as distinct from caller claims. | Their authorization-server and browser flow results are conditional on their web model and protocol assumptions. The resource transition here does not prove those flows. |
| [[https://openid.net/wordpress-content/uploads/2022/12/Formal-Security-Analysis-of-FAPI-2.0_FINAL_2022-10.pdf][Formal Security Analysis of FAPI 2.0]] | Model sender constraint explicitly. Select the DPoP or certificate check from the grant and refuse a mismatched mechanism. | FAPI's protocol and attacker model cover more than the resource boundary. This library claims neither full profile conformance nor session integrity. |
| [[https://www.rfc-editor.org/rfc/rfc9700.html][RFC 9700]], [[https://www.rfc-editor.org/rfc/rfc9449.html][RFC 9449]] and [[https://www.rfc-editor.org/rfc/rfc8705.html][RFC 8705]] | Check audience and scope against the actual target. For DPoP retain proof freshness, token hash, method, URI, key, nonce and replay state. For mTLS use the authenticated connection certificate. | The Lean checks assume sound cryptographic verification and trusted current observations. A useful counterexample is an authenticated, unexpired token presented to
a different resource audience. A second is a request using the right token
and certificate after revocation. Neither can satisfy the resource profile.
A captured DPoP proof can satisfy the same cryptographic checks on a second
worker. It is rejected by the modeled successor only if both workers consult
and update the same authoritative reservation state.

Future protocol proofs should model issuer selection and authorization-code
redemption separately from this resource layer. They should account for
redirect and session binding, PKCE, token substitution and key rotation before
making end-to-end claims. Downstream language libraries can refine the resource
Contract first by translating verified observations and proving their store
implements the same commit and revocation ordering.
