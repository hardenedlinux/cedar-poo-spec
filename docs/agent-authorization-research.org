* Research question and evidence

Reviewed on 2026-11-05 against the shared Zero Trust, Authorization Delta,
OAuth and Gateway models. The question is how current authorization can
preserve an application invariant as agent choices change future state.
Cryptographic identity, authorization non-expansion, semantic fact correctness
and trajectory safety are separate obligations.

The local contribution below is qualitative inductive safety over the existing
transition relation. It does not implement the discounted-MDP theorem or
reproduce a paper's experimental results. No universal decision procedure for
future agent behavior is claimed.

* Shared model improvement

Previously, =run_preserves= required every raw transition to preserve the
invariant independently of authorization. That rule remains valid. It is too
strong for an application whose raw action space includes dangerous actions
that its authorization boundary is intended to exclude.

=run_preserves_mediated= exposes the actual mediated-step premise in the
preservation law. =preservesInvariant step invariant= then supplies a statewise
requirement:

#+begin_example
invariant before AND
  for every after:
    step before (some effect) after -> invariant after
#+end_example

=Framework.atInvariant= adds this requirement through the existing strengthening
operation. =invariant_guard_preserves_framework= retains all original identity,
authorization, currentness, consumption, unknown-retention, revocation and
mediation requirements. =unsafe_successor_blocks= refuses an effect whenever
one possible successor violates the invariant. =unsafe_source_blocks= also
refuses an already unsafe observed state, even if the proposed target is safe;
source safety cannot disappear through a vacuous implication.

=invariant_guard_preserves_run= proves safety after every finite admitted
history from a safe initial state, given a separate preservation law for
unmarked transitions. Recovery, publication, fact updates and owner handoff
cannot disappear from this premise by being labeled maintenance.

The universal successor condition matters for nondeterminism: one favorable
sample cannot discharge it. An adapter must establish that its transition model
covers every actual successor. Omitting a dangerous outcome would invalidate the
implementation refinement. An empty transition relation establishes no progress.
The predicate is a Lean proof obligation, not a new Rust runtime analyzer.

The [[file:../CedarPooSpec/ZeroTrust/Continuous.lean][shared implementation]] extends the existing framework.
It adds no state store, token format, scheduler or alternative Cedar evaluator.

* Countermodels and scope

The existing [[file:../Tests/ZeroTrust/Functional.lean][functional model tests]] retain four distinct failures:

1. Identical authorization before and after a revision still admits a two-action
   path to an unsafe state. Same-world no-expansion alone cannot rule it out.
2. An action has both a safe and an unsafe successor. The invariant guard rejects
   it even though a favorable sample exists.
3. An unmarked rollback reaches an unsafe state despite effect guarding. This
   witnesses why the maintenance preservation premise cannot be omitted.
4. Conditional preservation is vacuous at an already unsafe starting state.
   The source-invariant check refuses a new effect even if its target is safe.

The positive law refuses an unsafe observed starting state, accepts a harmless
first action, refuses the newly dangerous
second action, and quantifies over arbitrary finite guarded runs. It does not
prove liveness, fairness, unbounded probabilistic value, semantic intent or
physical IO refinement. No new axiom or native decision oracle is needed.

Existing 51-domain Rust replay remains a consumer regression gate. It is not a
claim that each domain has already supplied a complete transition model and
proved this new invariant. Such an instantiation must name its actual states,
invariant, effect relation, maintenance relation and native coverage argument.

* Concrete OAuth lineage and recovery instantiation

The shared =Refresh.LedgerStep= relation already records actual enrollment,
sender-constrained refresh, revocation and unchanged-ledger transitions.
=Ledger.retains= now anchors two concrete obligations to an independently
selected historical ledger: every uniquely resolved access token keeps its
exact family and grant, and every committed family revocation remains present.

=step_retains_lineage= proves these obligations for every constructor, using
the real issuance freshness guards. =protectLineage= instantiates the shared
statewise invariant guard with this relation. =protected_lineage_preserves_run=
and =committed_run_retains_lineage= cover arbitrary finite histories.
=committed_historical_access_refused= needs the original token/family lookup;
it derives the later lookup instead of assuming the final reader supplies the
same association. A live unrelated family cannot adopt a revoked token digest.

The maintenance projection is concrete as well. Successful durable final-use
reservation retains the OAuth checkpoint. Actual revoke installation preserves
lineage; receiver handoff and confirmation preserve it, and
=ReceiptRecovery.trace_retains_oauth_lineage= covers both crash boundaries,
mapping commits and the existing receiver recovery trace. The real DPoP and
mTLS model exercises consume the typed issuance/revocation proof, and the
22-step receipt-recovery fixture retains this lineage law.

** Native representation boundary

Audit found a model/decoder mismatch: Lean =accessEntry= refuses a digest with
multiple matching rows, while default Rust =HashMap= deserialization silently
collapses duplicate JSON member names. The regression first reproduces that
acceptance, then checks the shared decoder's strict rejection before map
construction. Literal and escaped spellings of the same digest, either arrival
order, identical duplicates, and keys that differ from their grant digest are
refused. Valid serialized state keeps the same wire representation.

[[https://www.rfc-editor.org/rfc/rfc8259.html#section-4][RFC 8259, Section 4]]
recommends unique object names and describes inconsistent receiver behavior
for duplicates. This library deliberately adopts strict refusal to preserve
its unique-lookup semantics. The decoder checks representation consistency;
it does not authenticate arbitrary checkpoint contents or prove storage durability.

Rust controls exercise the actual persisted reader, reject ambiguous checkpoint
bytes without repairing them, and preserve historical token mappings through
issuance of an unrelated family, revocation and three writer takeovers under
both DPoP and mTLS. Old grants remain refused while the unrelated live grant
can still execute. The original recovery schedules, resource limits and complete
51-domain consumer gate remain unchanged.
