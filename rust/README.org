* Workspace ownership

The [[file:../Cargo.toml][root workspace]] owns the lockfile, shared dependency versions and immutable
ASP pin. All packages live under =rust/=, including shared libraries,
Host adapters, Case consumers and the CLI application (=bridge/=).
Case crates own scenario inputs, examples and external consumer tests. Libraries never
import Case crates or synthetic scenario inputs.

The [[file:commerce-mandate/README.org][mandate binding verifier]] and its independent Case feature
=ap2-checkout= consume the frozen SDK seed corpus. Verification supplies no
presentation permit, full UCP validation or stateful admission.

Commerce signatures are always present in the domain crate. Its optional
=projection= and =admission= features have no storage dependency. The Case
selects these capabilities. MRR-bound conditional commits, recovered credentials,
consumption and provider permits belong to =mrr-data-commerce= in MRR Data.
No package in this Cedar workspace imports MRR, including Case and dev dependencies.
Common pseudonymization and its Google contract compile without Cedar runtime;
Hosts explicitly compose runtime and domain libraries.

** Repository dependency direction

#+begin_example
mrr-data-commerce -> cedar-poo-commerce (admission)
                  -> mrr-data-content -> mrr-data-core
mrr-data-pseudonymization -> cedar-poo-pseudonymization (selected features)
#+end_example

MRR Data owns integration with its physical content protocol. Cedar provides
independent domain APIs and Lean models. =just check-rust= rejects direct MRR
dependencies in every Cedar workspace member and checks isolated normal dependency
trees for transitive MRR imports. A revision pin provides reproducibility;
it does not justify a reversed ownership edge.

The CLI keeps its command names, JSON formats and binary name. Library consumers
migrate directly to their owning crate; the bridge has no domain re-export
facade or old feature aliases.

* Optional evidence/effect simulation

The =gateway= feature retains one [[file:runtime/src/gateway/mod.rs][shared native owner]] for trusted field
sources, current review/effect binding, exact original consumption, signed
witness precommits, outcome receipts and independent public-key reconciliation.
The bridge exposes the corresponding catalogue, MCP stdio and auditor commands.
Default runtime/bridge builds exclude P-256; isolated feature gates check this.
=just check-effect-protocol= exercises the complete applicable catalogue and
real native child processes. The [[file:../docs/protocol/gateway-effect.org][protocol guide]] and [[file:../docs/protocol/gateway-effect-v1.schema.json][versioned wire schema]]
distinguish simulation evidence from deployed Host guarantees. This is not a
second Backend or a reverse MRR dependency.

* Choosing a Case and profile

A new Production Case should own its executable wiring and receipts in a Case
crate and select reusable profiles through normal dependencies. Shared profiles
belong in domain crates; provider-specific admission belongs in a Host adapter.
Two Cases may share a profile or choose different additive features. Features
select compiled capability; current keys, policy epochs and authority remain
trusted runtime inputs. A Cargo release/debug build profile is a separate
workspace build setting.

Do not put profile features on inherited workspace domain dependencies: each
Case declares its own choices. Dependencies use =default-features=false=.
Cargo may unify features on a shared dependency when building several Cases
together, so security checks must remain explicit and isolated builds are part
of =just check-rust=. See the [[https://doc.rust-lang.org/cargo/reference/features.html#feature-unification][Cargo feature unification reference]].
The gate discovers workspace members through Cargo metadata and rejects libraries
that import Case or CLI packages.

#+begin_src sh
cargo check --locked -p cedar-poo-commerce --no-default-features --features admission
just check-agentic-ai-commerce-admission
LEAN_PROJECTION_FIXTURE="$PWD/.lake/build/agentic-ai-commerce-projection.json" cargo test --locked -p cedar-poo-commerce-case --features consumption
just example health pseudonymization-google-contract
cargo run --locked -p cedar-poo-bridge -- replay-validated-receipts < manifest.json
#+end_src

The stable Just/Python entrypoints choose packages explicitly. =just check-rust=
checks dependency isolation, each package's defaults, individual Commerce
profiles, all workspace targets with all features, formatting and strict Clippy.
Fixture-dependent Cedar Commerce tests run in the conformance gate after Lean export;
the Rust-only gate runs all other workspace tests and the standalone admission consumer.
The actual Lean export is compared with =Tests/Conformance/commerce-projection-v1.json=,
which MRR Data pins for its integration consumer tests. The projection/admission Just checks export actual Lean fixtures before
running the external Case consumers.

* Google table transformation contract

[[file:pseudonymization/src/google_sdp.rs][google_sdp.rs]] maps the selected Lean table input to the official Google
Sensitive Data Protection =projects.locations.content.deidentify= and
=reidentify= REST body shapes. It selects one entire table column through
=RecordTransformations.FieldTransformation=, takes the context from a second
column, and uses a Host-resolved KMS-wrapped data key. The same transformation
configuration is used in the reverse request. The [[file:../CedarPooSpec/Pseudonymization/README.org][public Lean capability]]
owns the generic recipe; the [[file:../Examples/Health/Pseudonymization/README.org][hospital example]] supplies a synthetic selected row.

The =SelectedTabularInput= and =WrappedKeyBinding= must agree on key domain,
token-key version, and wrapping version before a request is constructed. The
Host must authenticate both inputs and resolve the actual key. This check
does not prove that the wrapped bytes contain that version of the data key.

The caller supplies a provider response through an authenticated transport.
=check_deidentify_response= and =check_reidentify_response= require the
expected table shape, unchanged context, one reported successful field
transformation, and the expected transformation or recovery of the selected
cell. De-identification also checks the Base64 AES-SIV token and any declared
surrogate name and encoded length. Their output binds hashes of the request
and response JSON. An
arbitrary JSON document can satisfy the shape check; it is not itself proof
of Google execution, a persisted audit, or atomic Host admission.
The [[file:pseudonymization-case/examples/pseudonymization_google_contract.rs][offline example runner]] consumes two explicitly synthetic provider-shape
responses from the hospital scenario and emits request/response digests.
The [[file:google-sdp-host/src/host.rs][in-memory admission API]] replays a schema-validated Cedar case,
binds the selected row, Google endpoint, and exact request body, and releases a caller-supplied
response only after a digest audit entry is appended. The
[[file:pseudonymization-case/examples/pseudonymization_google_admission.rs][hospital consumer]] owns synthetic responses in its scenario directory.
The in-memory Host records a digest of each admitted token with its dataset,
tenant, context, token-key version, and transformation revision. Recovery requires
that lineage; a token with no prior admitted issuance is rejected. This
registry is process-local evidence and does not authenticate a Google response
or replace a durable token catalog in a deployed Host.
The API has no embedded fixture. Its audit and approval revision live only in
process memory, so this does not establish durable or provider-authenticated
execution.

[[https://docs.cloud.google.com/sensitive-data-protection/docs/reference/rest/v2/projects.locations.content/deidentify][Google de-identify REST method]],
[[https://docs.cloud.google.com/sensitive-data-protection/docs/reference/rest/v2/projects.locations.content/reidentify][Google re-identify REST method]], and
[[https://docs.cloud.google.com/sensitive-data-protection/docs/reference/rest/v2/projects.deidentifyTemplates#CryptoDeterministicConfig][CryptoDeterministicConfig reference]] define the wire format.

* Approval-instance consumption

[[file:core/src/authority_consumption.rs][AuthorityLedger]] is a small Rust counterpart of the public
[[file:../CedarPooSpec/Admission/AuthorityConsumption.lean][Lean admission model]]. It matches one stable ID to one exact effect and
rejects missing, duplicate, mismatched, and exhausted grants. The
[[file:disclosure-host/src/host.rs][in-memory disclosure Host]] rechecks Cedar and consumes an approval
under the same lock as its budget, cohort, and audit update. The
[[file:disclosure-case/examples/agentic_ai_language_model_disclosure_host.rs][offline consumer]] exercises fresh-ticket replay, concurrent tickets,
separate approvals, and failure before consumption.

[[file:core/src/operation_identity.rs][OperationLedger]] binds a logical operation ID to its exact effect.
The Host checks it at preparation and commits it alongside approval use and
budget debit. The offline consumer rejects a fresh approval for the same
operation while allowing an independent operation with identical payload.

This lock gives process-local serialization only. A downstream Host must
authenticate the approval store and implement the same mutation in durable
transactional storage. It also needs an idempotent external-effect protocol:
the in-memory receipt does not prove delivery or resolve an uncertain sink
response after a crash.

* Local cryptographic check

[[file:pseudonymization-case/examples/pseudonymization_local.rs][pseudonymization_local.rs]] uses RustCrypto with a synthetic key to check
deterministic encryption, context separation, and local reversal after
governed Cedar decisions. Google internally expands its supplied key and
specifies its own context handling. The local RustCrypto output is therefore
not asserted to be byte-for-byte interchangeable with a Google token. The
Google request and response boundary above is kept separate from this local
check.

The [[https://github.com/tao3k/mrr-data/blob/feat/mrr-property-source-port/crates/mrr-data-commerce/src/budget_commit.rs][shared budget bridge]] checks one new reservation against the exact
current content CID and revision, fresh authority, immutable prior entries,
root and ancestor caps, global purchase and offer identities, and mandate ID
bindings. It then calls MRR Data's provider-neutral conditional commit
protocol. A returned =Apply= is a proposed transition. The backend must compare
and persist the head and operation receipt atomically; MRR Data supplies no DB.
The [[https://github.com/tao3k/mrr-data/blob/feat/mrr-property-source-port/crates/mrr-data-commerce/tests/integration/commerce_commit_consumer.rs][consumer test]] uses shared before/after JSON emitted by Lean.

The =commit_shared_reservation= API binds an explicit operation ID to the proposed
purchase, then invokes MRR Data's async atomic commit port. The Host supplies
fresh current authority inside the transaction callback; the adapter synchronizes
that authority through persistence. Confirmed commit, exact replay, known refusal,
and unknown outcome are distinct results. Exact recovery is effect-free and never
reserves again. The test-only provider checks concurrency, revocation after
preparation, unavailable authority or ledger, lost acknowledgement, and duplicate
offer attempts under a new operation ID. No concrete DB adapter is included.

The optional =ap2-coordination= feature supplies the [[file:../Examples/AgenticAI/Commerce/Coordination.org][co-located Checkout gate/journal contract]].
It groups Host-enrolled canonical authorization/agent/policy identities and
issues one whole-record CAS. Its independent consumer checks concurrency and
unknown ACK behavior; it supplies neither a durable backend nor a send permit.

* Complete Functional catalog replay

The bridge =replay-catalog= command consumes the official Lean manifest catalog.
It uses the runtime's existing strict schema-bound, raw-evaluation and schema
evolution replays. Deployment policies must match their schema-bound sources;
the tabular input is classified only as a data fixture. Unknown or incomplete
catalog shapes fail. =just check-functional-catalog= freezes all 48 original
manifest bytes and checks the 51-entry catalog.

Core =handoff::Scope<Actor>= and =Grant<Actor>= represent complete simulated
scope, current epoch and exclusive expiry. =CredentialMode= refuses empty input;
it does not certify that an arbitrary nonempty mode has an execution provider.
The bridge's settlement consumer parses actors as Cedar =EntityUid= and refuses
unsupported credential modes. It binds all claims and banking requests to their
actual schema-bound receipts, roots, actors and ordered phase requirements.
Fourteen scenarios exercise independent refusal boundaries; only =ready= admits.
These are replay simulations and do not issue credentials or execute settlement.

* Optional observations of actual replay

Runtime =replay_manifest_measured= and =replay_validated_manifest_measured= accept
ReplayMetrics and use the same conformance implementation as ordinary replay.
The ordinary path reads no clocks. Preparation and both compiled/rendered
Authorizer calls are observed independently; durations never feed admission.
Counters report actual per-manifest revision preparation and authorizer calls.
The bridge =benchmark-catalog= requires identical complete ordinary/measured
outputs across three fixed full-catalog samples and separately times transport
serialization. =just bench-functional-catalog= runs it as a release executable.
This is native Cedar conformance evidence, not native Lean or provider timing.

* Schema-local prepared reuse

The private replay owner reuses policies already loaded and strictly validated
within the current schema invocation. SourcePolicies seals the original source
body and revision alongside its parse; replay checks the complete binding before
using it. All strict validation still precedes request execution, and independent
rendered-text parsing/authorization remains required. The test-only original
workflow compares complete schema-bound catalog receipts and refusal errors.

=allocation-observation= is an opt-in bridge application feature. Its executable
uses a forwarding System allocator with nonallocating atomic counters. Ordinary
latency is measured without that feature; instrumented allocation/RSS observations
run separately. Rust allocation requests, requested-live peaks and OS process RSS
have different meanings and are never authority or admission inputs.

* P0-P2 shared native preparation

The [[file:../docs/native-preparation-acceptance.org][integrated acceptance report]] records invocation/schema-bound Entities
reuse, proved fused Contract reports, canonical hashing, full lifecycle/CPU/RSS
evidence and all-domain closure. Requests/decisions are never cached.

* Shared native preparation ownership

The runtime separates wire contracts/interning (=input=), SDK policy codecs
(=policy_codec=), immutable syntax contracts, source preparation and revision
binding, and Case/replay/schema execution. Dependencies follow that order;
preparation never imports the Case executor. Public crate APIs retain their owners.

Compiled policy sources are immutable shared snapshots. Schema reuse is explicitly
source-bound and retires with its declared input uses. Strict policy validation,
Contexts, Requests and authorizers execute independently. See the
[[file:../docs/native-schema-representation.org][complete schema/representation audit]] for source identity, parser error ordering,
allocator observations and the required full-domain proof/replay gates.

* Reviewed nonidentity effects

=just check-reviewed-effects= runs actual Lean C4 Delta analysis and POO Contract
transitions, then the shared native review/publication/effect simulation for all
applicable domains. The configured mock review authority and a separate gain
approval authority bind source, Schema, policy roots, compiled policies and
epochs. Opaque publication tickets install the actual candidate SDK receipt;
current effects never reuse the predecessor's Allow decision. Witness precommits
bind the complete signed publication prefix. Public audit and authority-bound recovery
retain both that prefix and the original consumption/unknown-exposure state.

=cedar-poo-bridge gateway-reviewed-stdio BUNDLE GROUP_INDEX --enforce|--shadow=
uses trusted startup analyzer output with the existing MCP owner. The
[[file:../docs/protocol/gateway-effect.org][protocol guide]] documents trust assumptions, refusal coverage and simulation
limits. No incoming MCP argument can certify a review or approve expansion.

* Current sources, revocation and recovery

The trusted simulated adapter exposes =refresh_facts=, =advance_time= and
=revoke= on the existing Simulator owner. Refresh evaluates fresh inputs under the exact strictly validated SDK sources
while retaining the exact original request, policies, Schema and consumed grant.
The new inventory has a current lease, a newer source generation and the actual
world commitment. Old evidence, handles and pending publication tickets refuse.
Time rollback refuses; expiry is checked at use and publication. Revocation
cannot be cleared by any renewal or recovery method.

=Simulator::recover(authority, evidence)= replaces both draft Case/history-only
recovery APIs. It requires the current surviving trusted authority, exact signed
publication prefix and independent historical audit configuration. It rotates
the mediator owner under the same deciding lock, retains current authorization
inputs and reconciles outcome evidence without reminting consumption. The old
facade is fenced from all use and writes. There is no serialized caller-selected
recovery checkpoint that can reset revocation or source freshness.

A different fact world requires fresh SDK preparation for effects. Publication
through an existing history additionally retains its pinned world; attempts
from another world refuse. Request/context changes require a newly authorized
logical operation. See the [[file:../docs/protocol/gateway-effect.org][boundary audit]] for the exact supported scope and
physical Backend obligations. The additional =gateway-lifecycle-catalog= phase
compares actual native effects and current state with Lean's POO lifecycle
Contracts across every qualified Case; the original matrices remain required.

=just bench-gateway-runtime= reports native API percentiles independently of the
full regression process. It covers all qualified Cases, warm handle preparation,
four-worker contention, SDK/source preparation and signed sends with a growing
1,024-operation witness. See the [[file:../docs/protocol/gateway-effect.org][measurement definitions]] before interpreting
these values as application latency. Witness history is owned append-only;
untrusted snapshots take full validation at restore and public audit boundaries.


Source preparation signs issuer-bound =FactStatement= batches, retaining every
field binding and exact inventory check. Independent issuers use separate keys;
no signature, current lease or generation check is removed. The native benchmark
retains per-Case samples in generated JSON and labels hot preparation, fresh
source preparation, full regression wall time and launch diagnostics separately.
See [[file:../docs/protocol/gateway-effect.org][the protocol and source preparation proof boundary]].


* Live Schema/Policy program ownership

=ValidatedProgram::prepare(schema, case)= validates the exact immutable source
pair and evaluates its first Case once, returning the owner and its receipt.
=replay(case)= accepts only the complete original policy source and evaluates
fresh Entities, context, request, expectations and both independent authorizers.
It reuses the existing Case evaluator and receipt constructor directly, without
rebuilding a source lookup map for a known single revision. =revise(case)=
shares the immutable Schema, validates a changed policy source before returning
a replacement owner, and evaluates that candidate afresh. A different Schema
requires a new preparation. Revision names, policy IDs and old Allow decisions
are never sufficient cache identities. Full source equality includes annotations
and signed-zero distinctions.

The original finite =SchemaPreparation= / =CatalogPreparation= APIs retain their
per-manifest validation behavior. The live owner is a separate explicit lifetime:
the simulator retains its current program, pending publication and in-flight
readers. Explicit caller-owned programs may also outlive individual operations. Dropping the last owner releases its parsed Schema
and policies; there is no unbounded process-wide source or request cache. Tests
observe actual Arc retirement, not just an entry-count estimate. Program objects
are not serialized checkpoints or execution capabilities.

=Simulator::with_prepared_release= constructs a new logical operation from an
explicitly supplied source owner, replays its current Case and binds the original
release as before. The deciding lock installs the new program with the reviewed
Case, SDK receipt and epoch. Renewal retains sticky controls, closes sources
before replay and checks generation again before installing fresh signed facts.
These source optimizations preserve the existing current-use/source Contracts.
The Lean =Functional.Ready.reuse_at_current_worlds= law joins actual typed Cedar
validation with independent evaluation at two supplied worlds. Native differential
checks compare complete receipts and signed initial operation state.

The seven pre-existing fixed simulation keys and the three-source key inventory
now have explicit process ownership, so each operation does not derive the same
provider keys again. This retains the same separate issuer identities and exact
signature checks. Facts, leases, world generations, availability and grants stay
operation-local. Real provider credential rotation and custody are not supplied
by these fixed mock keys. The independent provider-outcome role uses an eighth
cached key, distinct from Gateway, witness, source, review and approval roots.
A provider signature attests its own outcome domain; it is not a Gateway signature.

=bench-gateway-runtime= retains fresh-source preparation and constructor samples,
and adds =program.prepare=, =sdk.replay.prepared= and
=operation.construct.shared-program=. Program bootstrap includes its first SDK
evaluation and is reported separately. All 211 group bootstrap samples and all
1,253 per-Case samples remain in native JSON and timing-only CI logs. The distinct
1,024-operation append control shares one explicit program while evaluating each
operation afresh. Its single bootstrap sample is not a latency distribution.
The expanded API process has a different workload from the earlier observer;
whole-process comparisons use the unchanged complete lifecycle command instead.


The matched lifecycle sample set retained three complete before/after pairs with
identical output bytes. User CPU fell in all three pairs, but one wall sample
regressed (43.636 to 45.335 seconds). Its OS process elapsed also grew; the outer
observer gap was only about 65 ms. That is not evidence of stable wall-time
acceleration. Full results and resource limitations are recorded in the protocol
guide; failed and non-winning samples are not selectively rerun or omitted.

* Independent provider completion evidence

A lost Gateway receipt can be reconciled through
=ProviderJournal::signed_outcomes= and =reconcile_provider_outcomes= with explicit
=ProviderAuditTrust=. The distinct provider signature covers a versioned domain,
exact witness precommit, full action/result and original source/publication
material. The existing public auditor supports this mode using a trusted
=provider_key= plus detached =provider_outcomes=; mixed or downgraded modes fail.

=Simulator::recover_with_provider_outcomes= still requires the surviving
retained intent and generation fence. Completion clears historical uncertainty,
keeps the original burn and current resource/revocation/source image, and never
resends. Missing, invalid or uncorroborated proofs retain uncertainty. Plain
serialized journals remain read-only observations, not live provider authority.
Provider record durability and eventual delivery are not supplied by this
in-memory model. See [[file:../docs/protocol/gateway-effect.org][the shared boundary and evidence audit]].

The surviving authority also retains the original immutable fact interpretation
at precommit. Both recovery channels use that historical source window while
preserving the current clock, renewal, source quarantine/repair and SDK world.
A supplied current audit view must retain the same issuer roots; replacing them
is refused before ownership changes. This historical audit cannot renew current
authorization or remint a consumed effect. See the shared protocol's historical
source authority section for the typed laws and full Case matrix.

For a shared log, =reconcile_intent= / =IntentAuditTrust= anchor the audit to exact
independently expected signed bytes. Every log record and outcome envelope is
verified before unrelated operations are selected out; the complete signed-pair
index reuses authenticated Commit metadata without repeated signature/JSON work; same-operation ambiguity
remains a refusal. The existing CLI accepts an intent only in trusted setup and
marks scoped output explicitly. Global audit findings remain distinct. The
native append Benchmark preserves its 1,024 samples and adds 1,026-record scoped
recovery, with independent audit, revocation/source controls and native byte-buffer
capacity observations. See the shared protocol for the full boundary matrix and
all non-winning performance/resource observations.

Recovery retains an authenticated witness frontier in the surviving authority.
Subsequent recovery or send must extend the same prefix, even when an older valid
checkpoint still contains the original intent. The frontier advances with the
existing owner/generation update; source renewal and historical metadata cannot
reset it. See the protocol's shared-log progress section for signed rollback/fork
controls, Lean history Contracts and the limits of per-authority continuity.
